# Pemindahan domain ke `metmalcommunityspace.web.id`

**Tanggal:** 2026-09-18 18:49 WIB
**Cakupan:** dua repo — `medprom-metmal` (API) dan `dashboard-calendar-event`
(komunitas: SPA + API + media R2)
**Status:** kode selesai & ter-push · **deploy terblokir menunggu DNS**

## Tujuan

Mengganti domain `andotherstori.my.id` → `metmalcommunityspace.web.id` pada
seluruh permukaan: CDN media, API medprom, dan API komunitas.

Catatan ejaan: domain terdaftar **`metmalcommunityspace`** (dua huruf "m" di
*community*). Versi tiga-"m" yang sempat ditulis tidak ada di DNS.

## Pemetaan akhir

| Host baru | Origin | Menggantikan |
|---|---|---|
| `cdn.metmalcommunityspace.web.id` | R2 bucket `metmal-gallery` (custom domain) | `cdn.andotherstori.my.id` |
| `promapi.metmalcommunityspace.web.id` | VPS `127.0.0.1:3002` (`medprom-api`) | `promapi.andotherstori.my.id` |
| `api.metmalcommunityspace.web.id` | VPS `127.0.0.1:8080` (`metmal-nginx`) | `metmal.andotherstori.my.id` |

Dua API punya origin **berbeda** — ini mudah tertukar:
`promapi` → 3002 (API medprom saja), `api` → 8080 (nginx komunitas yang
melayani SPA `/` **dan** `/api/v1/*` sekaligus).

## Insiden: migrasi tidak sengaja dijalankan ke produksi

Saat menguji script migrasi di VPS, `--dry-run` **tertelan pembungkus shell**
(`sh -c ... -- --dry-run` diteruskan ke `sh`, bukan ke node), sehingga script
berjalan dalam mode tulis dan mengubah **67 baris** database produksi komunitas
ke domain yang saat itu **NXDOMAIN**. Gambar komunitas sempat tidak tampil.

**Pemulihan** (diverifikasi): 0 baris domain baru · 67 baris domain lama pulih
· 0 gambar rusak di beranda & galeri produksi · URL CDN langsung `HTTP 200`.
Tidak ada data hilang — hanya hostname; objek R2 tidak pernah disentuh.

**Pencegahan:** bawaan script dibalik menjadi lapor-saja. Kegagalan meneruskan
flag kini berakibat "tidak terjadi apa-apa", bukan kerusakan data. Diuji ulang
ke produksi: tanpa flag melaporkan 67 baris, DB tetap 0.

**Pelajaran proses:** jangan menjalankan perintah yang menulis ke database
produksi tanpa memverifikasi flag benar-benar diterima, dan selalu catat
`SELECT` sebelum-sesudah.

## Temuan keamanan: Caddyfile aktif ≠ repo

Caddyfile yang aktif di `/etc/caddy/Caddyfile` ternyata hanya
`reverse_proxy 127.0.0.1:3002` — **tanpa** `header_up X-Real-IP`, tanpa header
keamanan, tanpa log, padahal versi repo memuat semuanya.

Konsekuensi (diverifikasi probe terisolasi): Caddy **meneruskan** `X-Real-IP`
kiriman klien apa adanya (kirim `9.9.9.9` → origin menerima `9.9.9.9`).
`rateLimit.js` memakai header itu sebagai identitas klien, jadi identitas
**spoofable** bila tidak ada proxy di depan yang menimpanya.

- `promapi.*` — aman: Cloudflare menimpa header. Diverifikasi tegas: 61
  request dengan `X-Real-IP` berbeda-beda (`10.0.0.1`..`10.0.0.61`) berakhir
  60× `400` lalu `429` → identitas tetap IP asli pengirim, bukan header.
- `metmal.andotherstori.my.id` — **DNS-only** (langsung ke VPS, tanpa
  Cloudflare), jadi tidak ada yang menimpa → rate limit bisa dilewati.

Tercatat sebagai pitfall #18–20 di `AGENTS.md`.

### Koreksi: `{remote_host}` ternyata SALAH

Draf pertama Caddyfile memakai `header_up X-Real-IP {remote_host}` (mengikuti
komentar lama di repo). Itu **keliru untuk domain di balik Cloudflare**:
`{remote_host}` = alamat Cloudflare, sehingga **semua** pengunjung berbagi satu
bucket rate limit — satu orang bisa mengunci pengguna lain.

Yang benar, sudah diuji di VPS dengan dua skenario:

```
{ servers { trusted_proxies static <CIDR Cloudflare> } }
reverse_proxy 127.0.0.1:3002 { header_up X-Real-IP {client_ip} }
```

| Skenario | `X-Real-IP` diterima origin |
|---|---|
| peer tepercaya (Cloudflare) + XFF `9.9.9.9` | `9.9.9.9` (IP pengunjung asli) |
| penyerang langsung (tak tepercaya) + XFF dipalsukan | alamat TCP asli |

Catatan sintaks: `trusted_proxies` di dalam blok `reverse_proxy` **tidak valid**
(Caddy menafsirkan argumen pertama sebagai IP); harus di `servers` global dengan
kata kunci `static`. Caddyfile hasil perbaikan lolos `caddy validate`.

## Verifikasi kanal unggah Google Drive (2026-09-18)

Item pending lama "validasi unggah Drive di produksi" **selesai diverifikasi**:

- **Kredensial Google Drive di VPS KOSONG.** `GOOGLE_CLIENT_ID/SECRET/REFRESH_TOKEN`
  dan `DRIVE_ROOT_FOLDER_ID` semuanya 0 karakter di container `medprom-api`,
  padahal `docker-compose.yml` sudah meneruskan keempatnya. Konsekuensi:
  `POST /api/v1/drive/upload` dan `GET /api/v1/drive/status` membalas **503**
  (`driveReady === false`) — fail-closed sesuai desain.
- **Kredensial di `.env` lokal VALID.** Diuji langsung: refresh token ditukar
  di `oauth2.googleapis.com` → sukses, akun
  `mediapromosi.metmalbekasi@gmail.com`, scope `drive.file`, kuota 5 TB
  (terpakai ~155 GB). Artinya tinggal dipindahkan ke `.env` VPS bila ingin
  diaktifkan.
- **Frontend produksi SUDAH menyembunyikan kanal unggah.** `VITE_PROMO_UPLOAD_MODE=0`
  (ada sejak 2 hari sebelum catatan ini). Tenant melihat pesan "Kanal unggah
  berkas sedang tidak diaktifkan pada instance ini — silakan kirim tautan
  materi Anda", **bukan** tombol yang pasti gagal. Jadi **tidak ada bug yang
  dilihat pengguna**; keadaan konsisten antara FE dan server.

Keputusan pemilik produk: **biarkan tersembunyi** untuk sekarang. Mengaktifkan
unggah = pindahkan tiga kredensial ke `/opt/medprom/deploy/vps/.env`, restart
API, lalu uji unggah asli. Catatan: endpoint unggah bersifat **publik**, dijaga
rate limit 5/15 mnt/IP + allowlist MIME + magic bytes + maks 50 MB.

### Koreksi metode verifikasi (penting)

Saat memeriksa ini saya sempat menyimpulkan "kanal unggah TAMPIL di produksi"
berdasarkan adanya string `Unggah File` di bundle. **Kesimpulan itu salah** —
string tersebut juga berasal dari `SubmissionDetail.tsx:261`, komponen lain.
String penentu adalah `aria-label="Cara mengirim materi"` (pemilih kanal) dan
teks fallback "sedang tidak diaktifkan", keduanya di berkas yang sama.

A/B membuktikan flag bekerja: `flag=1` → pemilih kanal ada, fallback tidak;
`flag=0` → sebaliknya. **Pelajaran:** jangan menyimpulkan perilaku runtime dari
satu string di bundle hasil minifikasi; cari string yang unik pada cabang
kondisionalnya, atau uji A/B build dengan flag berbeda.

## Insiden kedua: `/events/:id` 502 di produksi (sudah dipulihkan)

Commit `27f39ca` mengubah rewrite `/events/:id` di `vercel.json` (repo
komunitas) ke `api.metmalcommunityspace.web.id`. **Proyek Vercel komunitas
ter-deploy otomatis dari git**, sehingga perubahan itu langsung tayang padahal
host tujuan masih NXDOMAIN. Akibatnya `/events/:id` membalas **502** di
produksi selama ±30 menit.

**Pemulihan:** rewrite dikembalikan ke `metmal.andotherstori.my.id`, deploy
ulang, diverifikasi `/events/:id` kembali `200` dengan `og:title` benar
(commit `8adf171`). Halaman `/`, `/events`, `/gallery` tidak pernah terpengaruh
(selalu 200).

**Akar masalah:** saya memperlakukan `vercel.json` sebagai berkas yang "belum
aktif sampai di-deploy manual", padahal Vercel men-deploy dari git secara
otomatis. Perubahan konfigurasi hosting berlaku segera setelah push.

**Pencegahan yang seharusnya:** ubah rewrite **bersamaan** dengan pembuatan
DNS (atau sesudahnya), jangan sebelumnya. Untuk perubahan yang menunjuk host
belum ada, siapkan di branch/lokal dulu.
