## Perubahan

### 1. #8 - sisa hari periode terlihat oleh tenant

`src/components/promo/SubmissionDetail.tsx` (dipakai bersama halaman status
ber-token dan pelacakan nomor): baris "Periode" kini menampilkan sisa hari
setelah rentang tanggal, dihitung dengan `daysUntil(air_end_date, toIsoDate())`
(cermin `src/utils/pricing.ts`). Tiga bentuk: "N hari lagi", "berakhir hari
ini", "lewat N hari" (merah). `null` (tanggal kosong/tidak valid) tidak
menampilkan apa pun. Sebelumnya hanya rentang tanggal statis.

Catatan: angka dihitung dari tanggal perangkat klien; angka otoritatif tetap
milik server pada panel staf (keputusan C5 sisi FE tetap terbuka).

### 2. #4 - atomisitas alur revisi lewat kompensasi (opsi 2 dokumen)

`server/src/routes/promo.js` handler `POST /promo/submissions/:id/revision`.
Sebelumnya tiga tulis berurutan TANPA transaksi dengan UPDATE status lebih
dulu; bila langkah 2/3 gagal, status sudah berpindah dan materi lama sudah
tertimpa sementara versi/riwayat hilang.

Urutan kini dibalik menjadi dapat dikompensasi: **versi materi + riwayat lebih
dulu, UPDATE status sebagai langkah TERAKHIR**. Bila salah satu langkah gagal,
baris yang telanjur masuk DIHAPUS (`DELETE ... WHERE id = $1` memakai id dari
`RETURNING id`), sehingga status `perlu_revisi` tetap utuh dan tenant dapat
mengirim ulang.

`insertFileVersion` dan `insertHistory` kini mengembalikan hasil query
(`RETURNING id`) agar kompensasi presisi (menghapus baris yang tepat, bukan
"baris terbaru"). Pemanggil lain (`/promo/submit`) tidak terpengaruh karena
nilai kembalian diabaikan.

**Batas yang jujur:** ini BUKAN transaksi sejati. Masih ada jendela
antar-statement (mis. proses mati di tengah), tetapi tidak ada lagi keadaan
"status berpindah tanpa materi". Opsi 1 (transaksi sejati via `db.connect()`)
tetap membutuhkan izin pemilik karena menyentuh `server/src/db.js` dan mock
pada 17 berkas test.

### #3 - model akses revisi

`SubmissionDetail` menerima `StatusPageData`, yang di endpoint publik
(`/status/:token`, `/track`) SENGAJA tidak memuat `device_fingerprint` (batas
kepercayaan). Jadi klien TIDAK DAPAT mengetahui kepemilikan tanpa membocorkan
fingerprint. Menyembunyikan form di klien mustahil tanpa keputusan pemilik
(mis. server mengirim boolean `is_owner`). Server tetap menolak revisi dari
perangkat lain (404), jadi tidak ada lubang keamanan, hanya UX.

(keputusan produk), dan `__tests__/api/admin-cetak.test.js` mengunci SQL
pengingat serta cacah item.
